Test impact analysis for pytest

Run only the tests your change can break.

Karma follows every import from your change to the tests that depend on it, runs the ones most likely to fail first, and keeps flaky tests from breaking your build. It explains every decision, needs no setup or history to start, and nothing leaves your machine.

Why I built Karma

      
Your change has consequences. Only those consequences need testing.

    • 
      

    

    

      
My philosophy is simple: the more you fuck around, the more you find out.

      
So I was fucking around in open source, contributing wherever I could. One day I opened a pull request that changed a single comment. One line. No code.

      
CI ran the entire test suite. Every test, on every platform, for a change that couldn't possibly break anything. I sat there watching the progress bar, burning compute and patience. Then a flaky test that had nothing to do with me failed, and I had to run it all again.

      
That's when I found out: most CI doesn't know what your change actually touches, so it runs everything, every time.

      
So I kept fucking around. I read the git diff, parsed the imports, and traced which tests could actually be affected. That became Karma: your change has consequences, and only those consequences need testing.

      
Then I found out more. I found out the diff was comparing the wrong commits. I found out CI could pass green while running zero tests. I broke real projects on purpose, 47 times, to prove Karma never skips a failing test. Then I taught it to predict which tests will fail first and to stop flaky tests from breaking builds.

      
Run only the tests your change can break.

      
PPradyuman Sharma
Creator of Karma

        Meta's predictive test selection
        
Machine learning decides which tests to skip.

        
    
          
  • Trained on a large history of test outcomes in Meta's monorepo.
    • 
          
  • Halved the infrastructure cost of testing changes, running about a third of the tests that transitively depend on the modified code.
    • 
          
  • Still reports over 99.9% of faulty changes, and over 95% of individual test failures. The rest are skipped by design.
    • 
        

        
Machalica, Samylkin, Porth, Chandra. Predictive Test Selection, ICSE-SEIP 2019.

      

      

        Karma
        
Dependencies decide what runs. ML decides the order.

        
    
          
  • Every test that imports the change runs: 0 failing tests missed across 47 injected bugs.
    • 
          
  • Prediction only reorders the selection, so the likeliest failure surfaces first without trading away any test.
    • 
          
  • Works on day one with no history and no data platform, then learns locally from your own runs.
    • 
        

        
Same idea at a smaller scale, with a guarantee instead of a probability.

      

    

  







  

    

      
How it works

      
Four steps between your change and a green build.

    

    
    
      
  1. 1
    Find what changed
    A diff from the merge base: exactly what your pull request contains, plus uncommitted work when you run locally.
    git diff --raw merge-base
    2. 
      
  2. 2
    Trace the imports
    Every module is parsed once and cached by content hash; cold starts parse in parallel. The resolver follows pytest's own rules.
    ast, cached per file
    3. 
      
  3. 3
    Select, safely
    Walk reverse dependencies to every affected test. Dependency and config changes run everything; a git failure never passes empty.
    breadth-first search
    4. 
      
  4. 4
    Predict and run
    Order tests by predicted risk, retry failures to separate flaky from broken, and report straight into the pull request.
    pytest + JUnit results

        Case study · encode/starlette
        
A modular framework: most changes touch a few tests.

        
starlette is built from separate components: routing, requests, a dozen middlewares. Each of its 32 modules was broken in turn and the full suite of 1,277 tests run to find what really failed.

        
32 / 32bugs caught
40.8%test files skipped
1 to 4of 31 files, for most middleware

        
A CORS or GZip change runs one or two test files instead of 31. A change to the request core still runs everything, because everything depends on it, and it should.

        
Karma saves the most where code is well separated, and never trades away a failing test to do it.

      

      

        Case study · Textualize/rich
        
A library with a hub: safe, even when it can't skip.

        
Nearly every rich test imports rich.console, which imports most of the library. Fifteen modules were broken, with 1,007 tests as the judge.

        
15 / 15bugs caught
6.6%test files skipped
1 of 63for a change to prompt.py

        
Most changes rightly select almost everything; a change to prompt.py, which nothing central imports, ran the one test file that failed.

        
When everything depends on everything, Karma says so honestly, and prioritisation still puts the likeliest failures first.

Set up in your CI

      
One step on GitHub. A few lines anywhere else.

      
On GitHub, the Karma action runs in your job's own Python environment, fetches history on shallow clones, keeps .karma_cache/ between runs, and reports into the pull request. On every other CI, the karma command does the same work and writes a standard JUnit report.

Configuration

      
Optional. Sensible without it.

      
Everything lives in [tool.karma] in pyproject.toml. Unknown keys are rejected, so a typo never passes silently.

    

    

      

        
pyproject.toml


[tool.karma]
test-patterns = ["test_*.py", "*_test.py"]
source-roots = [".", "src"]
exclude = ["examples/*"]
extend-run-all-on = ["Dockerfile"]
prioritize = true
retries = 2

[tool.karma.mappings]   # what imports can't express
"tests/fixtures/*.json" = ["tests/test_loader.py"]
"app/templates/*" = ["app/render.py"]

Limits

      
What static analysis can't see, and what covers it.

    

    

      
Imports built from strings at runtime
Karma follows import, from … import, literal importlib.import_module("…"), pytest_plugins and doctest imports. A module name assembled at runtime is invisible to any static tool. Cover it with a [tool.karma.mappings] entry, or a nightly karma run --all.

      
Data files that tests read
A JSON fixture or template changing doesn't show up in imports. Map it to the tests or modules that use it in [tool.karma.mappings]; changed files with no known dependents are listed, never dropped silently.

      
Libraries with a central hub module
In rich, nearly every test imports rich.console, which imports most of the library, so most changes rightly select almost everything. Karma saves the most where components are separated, as in most applications and monorepos. Prioritisation still helps there: the likeliest failures run first.

      
Can I check it on my own project first?
Yes. python scripts/safety_check.py --package src/yourpackage breaks your modules one at a time, runs your suite, checks Karma selected every test that failed, and restores every file.
