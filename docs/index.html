Test impact analysis for pytest

Run only the tests your change can break.

Karma follows every import from your change to the tests that depend on it, runs the ones most likely to fail first, and keeps flaky tests from breaking your build. It explains every decision, needs no setup or history to start, and nothing leaves your machine.

Why Karma

      
Your CI runs thousands of tests that cannot possibly fail.

      
A one-line change to a billing module doesn't need the login tests. The existing ways around full runs each give something up.

    

    

      
Changed-file plugins
Run the test files you edited. Edit app.py and its tests are skipped.
misses dependencies

      
Coverage-based tools
Need a full instrumented run first, a database kept between runs, and slow every test while tracing.
need history, add overhead

      
Test-selection SaaS
Train on your history in someone else's cloud. Paid, and your code metadata leaves the building.
data leaves your machine

      
Build systems
Bazel and Pants are precise, but you adopt a new build system to get there.

Each one works on its own and makes the others better.

A logistic regression learns from your own history: failure rate, recent failures, co-failure with the files you touched, and distance from the change. Reordering only; no test is ever skipped.

GitHub Action

      
Drop it into any Python workflow.

      
It runs in your job's own Python environment, so the selected tests can import your dependencies. It fetches history on shallow clones, keeps .karma_cache/ between runs, and reports into the pull request.

    

    

      

        
.github/workflows/test.yml


jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0   # optional: saves Karma fetching history
      - uses: actions/setup-python@v6
        with:
          python-version: "3.13"
      - run: pip install -e ".[test]"
      - uses: Pradyuman-aviator/Karma@main
        with:
          prioritize: "true"   # likeliest failures first
          retries: "2"         # flaky tests warn, broken tests fail
          args: --explain

Configuration

      
Optional. Sensible without it.

      
Everything lives in [tool.karma] in pyproject.toml. Unknown keys are rejected, so a typo never passes silently.

    

    

      

        
pyproject.toml


[tool.karma]
test-patterns = ["test_*.py", "*_test.py"]
source-roots = [".", "src"]
exclude = ["examples/*"]
extend-run-all-on = ["Dockerfile"]
prioritize = true
retries = 2

[tool.karma.mappings]   # what imports can't express
"tests/fixtures/*.json" = ["tests/test_loader.py"]
"app/templates/*" = ["app/render.py"]

Limits

      
What static analysis can't see, and what covers it.

    

    

      
Imports built from strings at runtime
Karma follows import, from … import, literal importlib.import_module("…"), pytest_plugins and doctest imports. A module name assembled at runtime is invisible to any static tool. Cover it with a [tool.karma.mappings] entry, or a nightly karma run --all.

      
Data files that tests read
A JSON fixture or template changing doesn't show up in imports. Map it to the tests or modules that use it in [tool.karma.mappings]; changed files with no known dependents are listed, never dropped silently.

      
Libraries with a central hub module
In rich, nearly every test imports rich.console, which imports most of the library, so most changes rightly select almost everything. Karma saves the most where components are separated, as in most applications and monorepos. Prioritisation still helps there: the likeliest failures run first.

      
Can I check it on my own project first?
Yes. python scripts/safety_check.py --package src/yourpackage breaks your modules one at a time, runs your suite, checks Karma selected every test that failed, and restores every file.
